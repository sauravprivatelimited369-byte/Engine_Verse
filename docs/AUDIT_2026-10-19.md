## 1. Security incident — public issue #39 (items 1, 2, 10, 80) — CONFIRMED, OPEN

**Evidence.** Public issue
[#39](https://github.com/authorsauravkushwaha/Forge/issues/39)
`[learner-sync] @sauravkushwaha`, opened 2026-10-16 by the *old* static-copy
sync flow, still contained (verified 2026-10-19 via `gh issue view 39`) a
non-empty `password_sha256` field: the fast digest
`SHA-256("engineverse-v1:<username>:<password>")` documented in
`backend/engineverse/github_storage.py::hash_password_digest`. The username
is in the issue title, so the only unknown is the password itself, against a
fast hash — offline-cracking territory. This is exactly the exposure class
that PR #43 / audit F-01 removed from the *code*: snapshots are now
progress-only (`validate_snapshot` strips `password_digest`,
`password_sha256`, `email_sha256`, `phone_sha256`), the committed
`data/learners/registry.json` contains only empty credential fields
(re-verified by `TestPublicRegistryBoundary`), and
`.github/workflows/learner-data-sync.yml` triggers only on maintainer
`workflow_dispatch` / authorised `repository_dispatch` — it no longer
auto-commits public issues.

**What was attempted today.** Redacting the issue body and closing the issue
via the GitHub API from this environment returned
`403 Resource not accessible by integration` for both PATCH and comment:
the available token is a read-capable GitHub App integration and cannot edit
issues. **The hash is therefore still public at the time of writing. This
report does not claim otherwise.**

**Required operator actions (repository owner, in the GitHub UI):**
1. Edit issue #39 and delete the snapshot block (or delete the issue), then
   close it. Note GitHub may retain edit history internally — treat the
   value as permanently public regardless.
2. **Rotate the affected password everywhere it was ever reused** (any
   hosted Forge account and any other service). The static-copy
   device-local account uses the same fast digest; change that password too.
3. Do not post the value anywhere to "confirm" it — see
   `docs/INCIDENT_RESPONSE.md`.

**Defence-in-depth fix made today (code).** Even with credential fields
stripped server-side, the browser runtime still *adopted* credential hashes
from a pulled public-registry snapshot into the device-local account store
(`pages-live.js::mergeSnapshotIntoStore`:
`password_sha256: snapshot.password_sha256 || existing...`). A poisoned or
legacy registry entry could therefore overwrite a device-local password
hash. The merge now preserves **only hashes already stored on this device**
and ignores all credential fields in remote snapshots. Regression tests:
`TestRemoteSnapshotCannotSetCredentials`.

**Residual / honest limits.** Git history of `data/learners/registry.json`
was previously scanned (audit §6 addendum) and contained only empty digest
fields; public *issue bodies* are outside what a repository scan can see —
#39 proves old clients could put a digest there. Any other pre-fix sync
issues should be searched by the owner (`password_sha256` in issue search)
and handled the same way.
