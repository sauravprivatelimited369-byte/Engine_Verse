# n8n workflows for Meridian

Eight importable workflows live in [`n8n/workflows/`](../n8n/workflows). They are
generated by `scripts/build_n8n_workflows.py` and structurally validated by
`scripts/check_n8n_workflows.py`, so they stay consistent as they change.

This document is the operator's manual: what each workflow does, what it needs,
what it costs, and exactly which steps remain manual.

> **Status, stated first.** The workflows in this repository are configurations,
> not running automations. Nothing here has been imported into the owner's n8n
> workspace, because that needs a signed-in session this environment does not
> have. Every workflow imports **inactive**, with credential slots marked
> `REPLACE_WITH_…`, so importing one cannot spend money before you choose a
> credential. See §8 for the manual checklist.

## 1. Files

| File | Purpose | Runs on its own? |
|---|---|---|
| `01-student-copilot.json` | The assistant: Chat Trigger → validate/limit → OpenAI-compatible model → reply | After you pick a model credential |
| `01b-student-copilot-agent.json` | The same assistant on the AI Agent node, with 10-turn memory per session | After you pick a model credential |
| `02-feedback-intake.json` | Validate → consent → classify → store (optional) → acknowledge | Yes, minus storage |
| `03-content-drafting.json` | Draft → platform variants → review issue (optional) → **stop for a human** | Yes, minus model/GitHub |
| `04-onboarding.json` | Consent → idempotent record → one welcome message | Yes, minus mail/storage |
| `05-unsubscribe.json` | Withdraw consent, one click | Yes, minus storage |
| `06-analytics-rollup.json` | Measured metrics from the Meridian database; names what it cannot measure | Needs a Postgres credential to report numbers |
| `07-ops-monitoring.json` | Error Trigger → redact → dedupe → notify an admin | After you enable one notification node |

Import one assistant variant, not both. `01` has no LangChain node-version
dependency and is the safer default; `01b` adds conversation memory and needs the
AI Agent, chat-model and memory nodes bundled with recent n8n versions.

## 2. Getting the assistant live (the part that needs you)

### 2.1 Make the Chat Trigger public

1. Open your workflow (the one behind
   `https://authorsauravkushwaha.app.n8n.cloud/assistant`) or import
   `01-student-copilot.json`.
2. Open the **Chat Trigger** node.
3. Turn **Make Chat Publicly Available** on.
4. Set **Mode** to **Embedded Chat**. (Hosted Chat gives you an n8n-branded page;
   Meridian uses its own interface.)
5. In **Allowed Origins (CORS)**, enter the origins separated by commas:
   `https://sauravprivatelimited369-byte.github.io,http://localhost:8000`
   — add your own HTTPS origin if you self-host the full app. Never leave `*`.
6. Leave **Authentication: None** only if you want a public study assistant. If
   you set Basic Auth, the proxy must send those headers, which Meridian's
   client does not do today.
7. Copy the **Chat URL** shown in the node. It looks like
   `https://<instance>/webhook/<id>/chat`.
8. **Activate** the workflow.

> The URL you gave me, `https://authorsauravkushwaha.app.n8n.cloud/assistant`,
> redirects to `/signin?redirect=%2Fassistant` — it is the n8n editor route, not a
> public chat endpoint. It cannot be embedded. Step 7 above is what produces the
> embeddable URL.

### 2.2 Point Meridian at it

Self-hosted (recommended, keeps the URL server-side):

```bash
ENGINEVERSE_ASSISTANT_URL=https://<instance>/webhook/<id>/chat
```

GitHub Pages copy (published in the page by design):

```
Repository → Settings → Secrets and variables → Actions → Variables →
  ENGINEVERSE_ASSISTANT_PUBLIC_URL = https://<instance>/webhook/<id>/chat
```

Then re-run the **GitHub Pages** workflow.

### 2.3 Verify, once

```bash
python scripts/verify_assistant.py --url https://<instance>/webhook/<id>/chat
```

One message, one execution. Exit code 0 means an answer came back.

## 3. Workflow A — student assistance

```
Chat Trigger (public, Embedded Chat)
      │
      ▼
Guard question        length 2–800, control characters stripped,
      │               per-session budget of 20/hour (workflow static data)
      ▼
Allowed? ──no──▶ Refusal  (a fixed, honest message; no model call)
      │yes
      ▼
Model (OpenAI-compatible /chat/completions)
      │
      ▼
Shape reply           strips HTML, bounds length, shapes `{ output }`
      │
      ▼
Log metadata          disabled by default; character counts only
      │
      ▼
Reply                 the Chat Trigger returns this node's `output`
```

- The system prompt lives in the *Guard question* Code node (or the AI Agent's
  system message in `01b`). It sets tone, scope, honesty rules, language handling
  (answer in the student's language; Hindi/Hinglish supported) and the rule that
  the assistant must not claim capabilities it lacks.
- `max_tokens` is 800 and `temperature` 0.3. Both are editable in the HTTP node.
- The request body is Meridian's, not n8n's: `{"action":"sendMessage",
  "sessionId":"ev-…","chatInput":"…"}` → `{"output":"…"}`. The same contract as
  n8n's official widget, so `@n8n/chat` could be dropped in later without
  changing the server.

**Memory.** `01b` connects a *Window Memory* node keyed by `sessionId` and keeps
10 turns. Meridian's session id is stable for one UTC day per browser, so this
behaves like a normal chat session and resets overnight. No account data is in it.

## 4. Workflow B — feedback

```
Webhook /webhook/engineverse/feedback
   → Validate and sanitise   (length bounds, consent-gated email, category)
   → Valid?  ─no→ 400 with the specific problems
             └yes→ Store (optional) → Acknowledgement {ok, category}
```

- Contact details are stored **only** when `consent` is true. The checkbox is the
  lawful basis; the workflow refuses to keep an email without it.
- Categories are a small, explainable keyword map (bug, content, accessibility,
  account, request, other). No model is used, so a misclassification is a
  two-line fix rather than a prompt-engineering session.
- `dedupeKey` = category + first 120 chars + 10-minute bucket, with a unique
  index, so a double submit does not create a duplicate row.
- The Meridian site already has its own feedback route (`/support`, GitHub
  issues). This webhook is for an n8n-hosted form or a future integration; the
  site does not post to it today. Wiring it would mean adding a server-side
  forward to `web/api.py`, which was not done because it duplicates the existing,
  tested route without a new benefit.

## 5. Workflow C — learning content distribution

```
Manual trigger → Brief → Draft with model (disabled) → Platform variants
   → Open a review issue (disabled) → Await human review  ← deliberate stop
```

- **Human review is structural, not a suggestion.** The workflow ends at a node
  called *Await human review*; publishing is a person's action.
- Variants respect platform limits: blog (markdown), Telegram 3,800 chars,
  Instagram 2,100, YouTube title 95, WhatsApp 900. No hashtag stuffing, no
  engagement bait, no invented statistics — the prompt forbids them and the
  checklist asks a reviewer to confirm.
- No scraping, no private accounts, no automated bulk messages. Nothing is posted
  to any channel by this workflow.
- To use it: edit *Brief*, enable the model node, run once, then follow the
  checklist in the output.

## 6. Workflows D, E, F

**D — onboarding (`04`).** Webhook → consent check → `INSERT … ON CONFLICT`
returning `is_new` → welcome email only when `is_new`. Re-submitting the same
address cannot produce a second welcome. The unsubscribe link in the message is
filled in by the operator before enabling the email node.

**E — unsubscribe (`05`).** Webhook → validate → `UPDATE … consent = false`.
Consent is withdrawn rather than the row deleted, so the operator can prove the
request was honoured.

**F — analytics (`06`).** Daily schedule → two Postgres queries (assistant
counts/latency from `audit_logs`; feedback/subscriber/account counts) → aggregate
→ optional email digest. It reports **measured** rows only and names what it
cannot measure — unique visitors, referral sources and retention cohorts — rather
than estimating them, because Meridian loads no third-party analytics.

**G — operations (`07`).** Error Trigger → summarise (redacts `sk-…` keys, bearer
tokens and query strings; truncates to 500 characters) → deduplicate (one alert
per workflow per 15 minutes) → Telegram and/or email. Attach it to any workflow
under **Settings → Error Workflow**.

## 7. Optional database tables

The datastore nodes are disabled. Create the tables first, then enable the node
and choose a Postgres credential. **Decide a retention period** and schedule a
delete; the defaults below are suggestions, not policy.

```sql
-- Workflow A: operational metadata only. No question or answer text.
-- `session_ref` is the per-session digest Meridian generates; it is not an
-- account id and changes each UTC day.
CREATE TABLE IF NOT EXISTS assistant_events (
  id             bigserial PRIMARY KEY,
  occurred_at    timestamptz NOT NULL,
  session_ref    text        NOT NULL,
  question_chars integer     NOT NULL,
  answer_chars   integer     NOT NULL,
  model          text
);
CREATE INDEX IF NOT EXISTS assistant_events_occurred_at ON assistant_events (occurred_at);

-- Workflow B
CREATE TABLE IF NOT EXISTS feedback_events (
  id          bigserial PRIMARY KEY,
  occurred_at timestamptz NOT NULL DEFAULT now(),
  category    text NOT NULL,
  message     text NOT NULL,
  contact     text NOT NULL DEFAULT '',
  consent     boolean NOT NULL DEFAULT false,
  page        text NOT NULL DEFAULT '',
  dedupe_key  text NOT NULL UNIQUE
);

-- Workflows D/E. `email` is personal data: keep it only with consent.
CREATE TABLE IF NOT EXISTS newsletter_subscribers (
  id              bigserial PRIMARY KEY,
  email           text NOT NULL,
  name            text NOT NULL DEFAULT '',
  consent         boolean NOT NULL DEFAULT false,
  consent_at      timestamptz,
  unsubscribed_at timestamptz,
  dedupe_key      text NOT NULL UNIQUE
);

-- Example retention (adjust to your policy):
-- DELETE FROM assistant_events WHERE occurred_at < now() - interval '90 days';
-- DELETE FROM feedback_events  WHERE occurred_at < now() - interval '365 days';
```

The n8n Postgres nodes reference credentials as
`REPLACE_WITH_POSTGRES_CREDENTIAL`; importing does not create one.

## 8. Costs, limits and the manual checklist

### Execution accounting

n8n counts **one execution per message** to the Chat Trigger. A ten-message
conversation is ten executions. On top of that, each model call is billed by
your model provider. Pricing changes and differs by plan, so this document does
not quote figures — check your n8n plan's execution allowance and your
provider's price list before enabling a public chat.

Practical controls, in order of usefulness:

1. Set a **spend limit** in your model provider's dashboard.
2. Keep `max_tokens` small (800 here) and the model inexpensive.
3. Keep Meridian's per-IP and per-session limits on.
4. Keep the workflow's per-session budget in *Guard question*.
5. If n8n starts refusing executions, set `ENGINEVERSE_ASSISTANT_ENABLED=false`.
   The site keeps working; only the assistant stops.

### Manual checklist (owner only)

- [ ] Import `01-student-copilot.json` (or `01b`).
- [ ] Choose a model credential on the HTTP / chat-model node.
- [ ] Chat Trigger: public, **Embedded Chat**, Allowed Origins = your origins, Authentication=None.
- [ ] Copy the Chat URL.
- [ ] Set `ENGINEVERSE_ASSISTANT_URL` on the host (or the repository variable
      `ENGINEVERSE_ASSISTANT_PUBLIC_URL` for Pages) and redeploy.
- [ ] Run `python scripts/verify_assistant.py` and confirm an answer.
- [ ] Attach `07-ops-monitoring.json` as the Error Workflow of the others.
- [ ] Choose notification credentials (Telegram/SMTP) and enable those nodes.
- [ ] Decide retention for `assistant_events` / `feedback_events` / subscriber data.
- [ ] If using onboarding: create the tables, enable the nodes, insert the real
      unsubscribe URL, and test one subscribe and one unsubscribe.
- [ ] Confirm the model provider's data-retention terms match your privacy notice.

### What was not verified here

- Importing into a live n8n instance. The JSON is structurally validated, its
  embedded JavaScript is parsed with Node, and the HTTP contract is tested
  against a local server (`scripts/mock_n8n.py`), but node parameter schemas are
  n8n-version-specific and are only truly checked by importing.
- Any provider call. No API key was available and none should be committed.
- Execution counts or costs on your plan.

If a node shows a warning after import, it is safe to fix it in the editor: the
workflows are committed as generated files, and `scripts/build_n8n_workflows.py`
regenerates them if you prefer to change the source.
