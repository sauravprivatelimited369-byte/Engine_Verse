## 2. Confirmed findings, fixes, verification

### F-01 — P0 · CONFIRMED · Public "Learner Vault" stored password digests and allowed unauthenticated account takeover

- **Evidence:** `backend/engineverse/github_storage.py` stored fast SHA-256
  password digests (`engineverse-v1:<username>:<password>`) plus unsalted
  `email_sha256`/`phone_sha256` hashes in `data/learners/registry.json` in this
  **public** repository. `merge_records()` accepted a caller-asserted
  `password_changed_via_otp: true` to replace an existing learner's digest.
  `.github/workflows/learner-data-sync.yml` triggered on any public issue and
  pushed the merge straight to `main`. `POST /api/sync/snapshot` also accepted
  a client-supplied snapshot for an arbitrary username. This contradicted the
  README/SECURITY rule that the public repo must never contain learner data or
  password hashes.
- **Impact:** offline password cracking against a fast hash; enumerable email/
  phone hashes; takeover of any Pages-copy account by anyone with a GitHub
  account; unauthenticated progress forgery.
- **Fix:** registry is progress-only now — credential/identifier fields are
  stripped in `validate_snapshot()`, on merge, and on load (legacy values
  blanked); the `password_changed_via_otp` override is deleted; raw `email`/
  `phone` payload keys are refused; the browser snapshot builder sends empty
  hash fields; the sync workflow no longer triggers on public issues
  (maintainer `workflow_dispatch` / authorised `repository_dispatch` only);
  `POST /api/sync/snapshot` requires sign-in and builds the snapshot from the
  server DB for that user; GET responses exclude all credential-shaped keys;
  `docs/SECURITY.md` updated.
- **Verification:** new tests `test_registry_never_stores_credential_material`,
  `test_learner_sync_workflow_does_not_auto_commit_public_issues`,
  `test_sync_post_ignores_client_supplied_snapshot`,
  `test_sync_post_requires_sign_in`; updated merge/self-check tests assert the
  digest hex never reaches the file. All pass.
- **Residual:** Pages-copy accounts remain device-local with a fast local
  digest in the browser only (documented in SECURITY.md). Existing published
  git history should be checked by the owner for any digest that was ever
  committed (the current registry file contains only the owner's sample with
  empty digest fields); if one is found, treat that password as compromised.

### F-02 — P1 · CONFIRMED · Static-copy "judge" fabricated Accepted verdicts for compiled languages

- **Evidence:** `pages-live.js::executeSingleCase` — for C/C++/Java/C#/Go/Rust/
  SQL, any code containing a keyword (`for`, `HashMap`, …) or longer than the
  stub returned `status:"accepted"` with `stdout` copied from the test case's
  *expected* output. Submit then recorded the problem solved and awarded XP.
  `scripts/export_pages.py::enable_problem_editor` deleted the "Code execution
  is off" warning and enabled every language as if runnable. Run/Submit output
  was interpolated into `innerHTML` unescaped.
- **Impact:** fake success, fake solved/XP/certificate records on the public
  site; directly violates the project's own execution-honesty contract that
  the server side enforces in `test_coding_honesty.py`.
- **Fix:** non-runnable languages now return `unsupported_language` with
  `executed:false` and an explicit "your code was not executed" message;
  Submit shows **NOT RUN**, awards no XP and records no solve (also fixed a
  phantom "+3 XP" shown on wrong answers); language options are labelled
  "(cannot run here)" / "Python (browser subset)"; the exporter replaces the
  warning with an honest static-runner notice instead of deleting it; program
  output is escaped before `innerHTML` in Run/Submit.
- **Verification:** `TestStaticRunnerHonestyContract` (no expected-output
  copying remains, not-executed wording present, exporter notice asserted);
  existing exporter/pages contracts still pass; `node --check` passes.

### F-03 — P1 · CONFIRMED · Public site claimed capabilities the static host does not have

- **Evidence (live, 2026-10-18):** the Pages homepage said *"accounts, live
  code runner, labs, Android APK and GitHub progress sync work directly here"*
  and *"sync your progress to authorsauravkushwaha/Forge on GitHub"*;
  OTP previews said *"6-Digit Signup OTP Sent: Dispatched to … via Mobile SMS /
  Gmail. Instant verification code: …"*. A static host sends no SMS/email,
  keeps no server account, and (F-02) did not run most languages.
- **Fix:** homepage hero + sync section rewritten to distinguish hosted-app
  behaviour from the static copy (device-local accounts, JS + Python-subset
  runner, progress-only snapshots, GitHub is not the account database); all
  OTP previews/toasts and exported account-page descriptions now state the
  code is shown on-screen because nothing can be sent.
- **Verification:** contract test asserts none of the delivery claims remain;
  copy is true for both the hosted render and the Pages export.

### F-04 — P1 · CONFIRMED · Settings/provider caches made the test suite order-dependent (10 full-suite failures)

- **Evidence:** `judge.resolve_provider()` cached for the process lifetime
  while `get_settings()` is separately `lru_cache`d. The
  `disabled_judge` fixture reloaded settings during teardown *before*
  monkeypatch restored `ENGINEVERSE_JUDGE`, caching `disabled` for every later
  test. Reproduction: full suite failed 10 judge tests with
  `unsupported_language` while `provider_info()` captured at import said the
  sandbox was available; each test passed alone.
- **Fix:** provider cache keyed on a settings fingerprint (judge mode, Judge0
  URL, production flag, Java paths) so a reload takes effect; fixture undoes
  the env patch before reloading; a `pytest_runtest_teardown` wrapper hook in
  conftest drops both caches after each test's finalisers run, making the
  suite order-independent.
- **Verification:** previously failing combination
  (`test_coding_honesty.py` + judge tests) passes; full suite green.

### F-05 — P2 · CONFIRMED · `POST /api/sync/snapshot` always returned 500

- **Evidence:** handler called `ratelimit.allow(...)`; the module's API is
  `ratelimit.check(...) -> RateLimitResult`. `AttributeError` reproduced with a
  `TestClient(raise_server_exceptions=True)` script. No test had ever POSTed
  to the endpoint.
- **Fix:** use `ratelimit.check(...).allowed`; new tests exercise the POST
  path authenticated and anonymous (with F-01 changes).

### F-06 — P2 · CONFIRMED · Tutor presented unrelated notes as grounded answers

- **Evidence (probe against seeded DB):** "what is the current stock price of
  Tesla" → grounded answer about break-even mining economics; "write a poem
  about the moon in French" → file-systems notes; "how do I cook rice in a
  pressure cooker" → vapour-pressure notes (substring `rice` ⊂ `price`).
  Causes: one generic content-word match sufficed, substring matching,
  instruction verbs ("explain") counted as subject words, and named terms
  (Tesla/French) were never checked.
- **Fix:** instruction verbs are stopwords; search uses content words; ≥3
  content words require ≥2 distinct whole-word (plural-tolerant) matches, or
  a title match for short questions; a capitalised named term that no hit
  mentions refuses the answer. Measured after fix: in-scope set 7/7 grounded
  with citations (an 8th probe, "pointers in C", now honestly reports related
  material only — the catalogue has no pointers note, previously it
  "grounded" in an arrays note); out-of-scope set 6/6 refused.
- **Verification:** `TestTutorEvalSet` parametrises both sets permanently.

### F-07 — P2 · CONFIRMED · Leaderboard period filter never worked, fields blank, privacy opt-out ignored

- **Evidence:** page submits `period=week|month`; `progress.leaderboard()`
  recognised only `weekly|monthly`, so the page's period ranking was silently
  all-time. Query aliased `current_streak AS streak` and returned no `topics`,
  while `leaderboard.html` renders `row.current_streak` and `row.topics`
  (blank/0). Users with `privacy.showProgress=false` (which hides portfolio
  stats) were still ranked by name/XP/streak.
- **Fix:** one `LEADERBOARD_PERIODS` map accepting both spellings (API and
  page share it); rows carry both `current_streak` and `streak` plus completed
  `topics`; query excludes `showProgress=false` via `db.json_flag`; page copy
  now defines XP as activity, not mastery, and notes the opt-out.
- **Verification:** `TestLeaderboardAuditFixes` (backdated XP events prove
  week≠all ranking; field presence; opt-out removal); live check of
  `/api/leaderboard?period=week` returns the new fields.

### F-08 — P2 · CONFIRMED · Settings preference checkboxes ignored stored values

- **Evidence:** `settings.html` hard-coded `checked` on privacy/notification
  boxes; `settings_context()` never loaded the stored JSON. An opted-out user
  saw everything "on", and saving the form for any reason re-enabled it.
- **Fix:** context parses `privacy`/`notification_prefs` with registration
  defaults (`_stored_prefs`); template renders each box from stored state;
  show-progress label notes it also controls the leaderboard (F-07).
- **Verification:** test sets stored prefs off, asserts unchecked rendering,
  re-saves as a browser would, asserts they stay off.

### F-09 — P2 · CONFIRMED · Raw diagram hotspot JSON emitted with `|safe` inside a single-quoted attribute

- **Evidence:** `topic.html`: `data-hotspots='{{ diagram.hotspots | safe }}'`
  used the raw DB column. One apostrophe in hotspot text ("Bernoulli's…")
  terminates the attribute; crafted text could inject attributes. (The SVG
  `spec` next to it *is* sanitised via `sanitize_svg` — verified OK.)
- **Fix:** render the parsed `hotspots_data` with `| tojson | forceescape`
  inside a double-quoted attribute (verified round-trip:
  `JSON.parse(unescape(attr))` reconstructs the value, markup cannot break
  out); caption condition uses the parsed list.
- **Verification:** template assertion + escaping round-trip test; live topic
  page shows `data-hotspots="[{&#34;explain&#34;: …}]"`.

### F-10 — P3 · CONFIRMED · Numeric env vars failed with an anonymous ValueError; no range checks

- **Evidence:** `Settings` used bare `int(os.environ.get(...))`;
  `ENGINEVERSE_JUDGE_TIMEOUT_MS=5s` crashed startup without naming the
  variable. Non-positive session/judge values were accepted in production.
- **Fix:** `_int(name, default)` raises `RuntimeError` naming the variable;
  `production_problems()` rejects session values < 1 and judge limits below
  the local runner's own floors. Tests cover both.

### F-11 — P3 · CONFIRMED · Three search inputs had no accessible name

- `books.html`, `formulas.html`, `search.html` inputs had only placeholders.
  Added `aria-label`s. (Everything else spot-checked: skip link, `aria-label`s
  on icon buttons, `:focus-visible`, `prefers-reduced-motion`, label-wrapped
  inputs — present. This is **not** a WCAG conformance claim; no full
  assistive-tech audit was performed.)

### F-12 — P3 · CONFIRMED · Footer promised "free and always will be" + a Premium tier that does not exist

- `free_tier_note` (brand default + seed) advertised Premium extras
  (certificates, unlimited AI tutor). No purchasable plan exists (`pro`/`team`
  are seeded inactive; no checkout). Reworded to state the instance is free to
  use, there is no paid plan here, and certificates are not accredited.

  (was 30/8/3 for first/repeat/failed).

  0; streak check-in no longer mints XP; flashcard/community awards aligned
